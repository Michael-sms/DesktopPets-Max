# 个人二次元桌宠制作计划

## 1. 项目目标

用户上传一张本人、宠物或原创角色照片后，系统依据统一的角色设计规范，将照片转化为具有稳定外观的二次元桌宠，并产出可直接接入桌面应用的透明动画资源。

首版桌宠至少包含以下四类状态：

1. **静置（Idle）**：没有任务时自然呼吸、眨眼，并偶尔做轻微随机动作。
2. **鼠标悬停（Hover）**：感知指针靠近或停留，抬头、看向指针并作出友好回应。
3. **加载中（Loading）**：系统正在等待或处理，但尚未开始明显工作时，展示持续且不焦躁的等待动作。
4. **工作中（Working）**：任务正在执行时，展示专注、连续、有节奏的工作动作。

最终体验应接近原生 Codex 桌宠的核心特点：状态容易辨认、动作简洁有生命力、切换自然、不遮挡主要工作区域，同时保留上传照片中最有辨识度的个人特征。

## 2. 首版范围

### 2.1 包含内容

- 单张照片上传与基础质量检查。
- 从照片中提取角色身份特征，生成二次元角色设定稿。
- 生成四类状态动画，以及状态间必要的过渡动画。
- 自动抠图、统一尺寸、切帧、打包和生成资源清单。
- 在桌面透明窗口中播放动画，并响应鼠标和任务状态。
- 提供一次“角色设定确认”和一次“动画整体验收”的人工审阅节点。

### 2.2 首版不包含内容

- 根据多张照片训练专属模型。
- 3D 建模、骨骼动画或实时口型同步。
- 自动模仿特定在世艺术家的画风。
- 复杂桌面漫游、攀爬窗口、物理碰撞和多桌宠互动。
- 未经确认就自动发布或上传用户照片、生成素材。

## 3. 输入要求

为了让一张照片足以稳定还原角色，上传界面需要明确提示：

- 推荐正面或轻微侧脸，脸部无遮挡且对焦清晰。
- 光线均匀，避免强逆光、重度滤镜和极端表情。
- 建议包含头部、上半身和主要服装；若只含面部，系统需自动补全服装设定并标记为推测内容。
- 单人/单主体照片最佳；多人照片必须让用户选择主体。
- 支持 JPG、PNG、WebP；建议短边不低于 1024 px。
- 用户需确认拥有照片和人物形象的使用授权。未成年人照片、真人公众人物和敏感内容需要额外限制。

上传后执行自动检查：主体数量、清晰度、遮挡程度、裁切完整度、图片方向与背景复杂度。若照片无法可靠提取特征，要求用户更换图片，而不是继续生成低一致性的结果。

## 4. 角色设计规范

### 4.1 默认视觉方向

- 二次元 Q 版（约 2.5～3 头身），正侧兼容的三分之四视角。
- 清晰外轮廓、适量赛璐璐阴影、柔和高光，缩小后仍易辨认。
- 透明背景，无文字、边框、道具残片或投影底板。
- 默认画布 512 × 512 px，角色主体占画布高度约 80%。
- 默认朝右；需要看向鼠标另一侧时优先水平翻转，减少重复资源。

### 4.2 必须保留的身份锚点

首次分析照片后生成一份 `character_spec`，至少记录：

- 发型、发色、刘海和显著发饰。
- 眼睛颜色、脸型、眉形及可安全保留的显著特征。
- 主要服装颜色、领口、袖型和代表性配件。
- 主色、辅色和强调色的固定色板。
- 角色比例、线条粗细、阴影方向和表情强度。
- 不得出现的变化，例如突然增加帽子、改变发长、替换衣服或改变瞳色。

设定稿需要同时提供正面、三分之四视角、侧面、基础表情和固定色板。只有设定稿经用户确认后，才批量生成动画帧。

### 4.3 照片转二次元的生成策略

1. 对原照片做主体裁切和背景分离，仅将主体作为身份参考。
2. 先生成单张角色设定稿，不直接生成动作，降低后续漂移。
3. 将确认后的设定稿作为所有状态的共同视觉参考；提示词中固定服装、发型、比例、镜头和光源。
4. 优先生成“关键姿势表”，再由关键姿势扩展中间帧。
5. 每批生成后进行脸部、发型、服装、色板和轮廓一致性检测；不合格帧单独重做。
6. 禁止在每一帧中独立重新设计角色，以免出现闪烁和身份变化。

## 5. 动作设计

### 5.1 动作总表

| 状态 | 触发条件 | 动作表现 | 建议时长/帧数 | 循环方式 |
| --- | --- | --- | --- | --- |
| 静置 Idle | 无任务且鼠标未悬停 | 呼吸、眨眼、轻微晃动；低概率伸懒腰或左右观察 | 主循环 2.4 s / 12 帧；随机动作 1.5～3 s | 主循环连续，随机动作间隔 8～20 s |
| 鼠标悬停 Hover | 指针进入角色热区 120 ms 以上 | 视线跟随指针、抬头、挥手或轻微开心反应 | 0.8～1.2 s / 8～12 帧 | 停留时保持末端微动，移出后回 Idle |
| 加载中 Loading | 等待网络、模型响应、资源准备 | 抱住小沙漏/观察旋转光点/轻点脚尖 | 1.2～1.8 s / 12～16 帧 | 无缝循环，避免大幅快速动作 |
| 工作中 Working | 任务正在实际执行 | 专注敲击小键盘、翻页或操作悬浮终端 | 1.0～1.5 s / 12～16 帧 | 无缝循环，可偶发“灵感闪光” |

### 5.2 状态辨识原则

- **Loading 与 Working 必须一眼可分**：Loading 是“等待反馈”，Working 是“主动操作”。不能都只做敲键盘动作。
- Hover 的首个反应要在 150 ms 内开始，以产生“它发现了我”的感觉。
- Idle 动作幅度最小，避免持续抢夺注意力；Working 的节奏明确但不应闪烁。
- 所有循环首尾姿势、重心、光影和轮廓必须衔接，禁止明显跳帧。
- 动画遵循适度的预备动作、缓入缓出和轻微次级运动（头发、衣角、饰品）。

### 5.3 过渡动画

首版至少制作以下短过渡，每个约 4～8 帧：

- `idle_to_hover`、`hover_to_idle`
- `idle_to_loading`、`loading_to_working`
- `working_to_idle`

紧急状态变化允许先播完当前动作的可中断段，再进入目标状态；不要求每两个状态之间都有独立过渡。每段动画资源需标注可中断帧。

## 6. 生成与制作流水线

### 阶段 A：照片接收和特征分析

1. 校验格式、尺寸和主体质量。
2. 本地生成主体遮罩、裁切图和特征摘要。
3. 让用户选择保留真实服装，或使用默认主题服装。
4. 输出结构化的角色描述与隐私处理记录。

**产物：** `source.png`、`subject_mask.png`、`character_spec.json`。

### 阶段 B：角色设定确认

1. 生成 2～3 个风格一致但细节略有区别的候选设计。
2. 用户选择一个候选，并可修改发型、服装、配色和配件。
3. 输出角色转面、表情表和色板。
4. 将确认结果锁定为后续生成的唯一角色基准。

**审阅关卡 1：** 用户确认“像本人/主体”“喜欢该形象”“允许继续生成动作”。

### 阶段 C：动作关键帧

1. 先为四种状态分别生成起始、动作峰值和结束关键帧。
2. 将四组关键帧放进同一姿势表中检查身高、头身比和服装一致性。
3. 不一致时优先修关键帧，禁止带问题进入补帧阶段。

**产物：** `pose_sheet.png` 和逐状态关键帧。

### 阶段 D：补帧与动画清理

1. 根据关键帧生成或绘制中间帧。
2. 统一轮廓、色板、透明边缘和角色落脚点。
3. 修复手指、眼睛、头发、配件和道具在连续帧中的形变。
4. 检查首尾循环并调整帧时长；眨眼等快速动作可使用非均匀帧时长。
5. 生成 1× 原图与 0.5× 预览资源。

**产物：** 独立 PNG 帧、预览 GIF/WebP、可选 sprite sheet。

### 阶段 E：自动质量检查

对每个状态执行：

- 所有帧尺寸一致且具有 Alpha 通道。
- 非透明像素不越界，底部锚点偏移不超过 2 px。
- 色板和亮度没有非预期跳变。
- 相邻帧主体轮廓变化处于合理范围。
- 面部身份和服装特征与设定稿一致。
- 循环末帧到首帧无明显跳跃。
- 透明边缘无白边、黑边或背景残留。

自动检查只负责拦截明显问题，最终仍需人工观看完整循环。

### 阶段 F：资源打包与桌面集成

建议资源结构：

```text
assets/pets/<pet_id>/
├── manifest.json
├── character_spec.json
├── preview.png
├── idle/
├── hover/
├── loading/
├── working/
└── transitions/
```

`manifest.json` 至少包含：画布尺寸、显示缩放、每段动画的帧列表与帧时长、循环规则、热点区域、落脚锚点、可中断帧、默认朝向和资源版本。

## 7. 桌面端状态机

状态优先级建议为：`Working > Loading > Hover > Idle`。

- `Idle → Hover`：鼠标进入角色有效区域并停留 120 ms。
- `Hover → Idle`：鼠标移出后延迟 200 ms，避免边缘反复触发。
- 任意状态 `→ Loading`：收到任务但正在等待资源或响应。
- `Loading → Working`：收到明确的执行开始事件。
- `Working → Idle`：任务完成、失败或取消，先播放收尾动作。
- Hover 不覆盖 Loading/Working，可在忙碌状态中仅让眼睛短暂跟随指针。

桌面窗口要求：透明、无边框、置顶可配置、角色外透明区域点击穿透；角色实体区域可拖拽。拖动、右键菜单和关闭操作必须保留稳定热区，不能随动画轮廓剧烈变化。

## 8. 技术实现建议

结合当前项目的 Python 3.10+ 骨架，首版建议采用：

- **桌面窗口：** PySide6，负责透明无边框窗口、鼠标事件、系统托盘和动画定时。
- **资源格式：** 开发阶段保存透明 PNG 帧；运行时优先加载打包后的 WebP 或 sprite sheet，以降低文件数量与内存抖动。
- **状态管理：** 独立 `PetStateMachine`，业务任务只发送 `loading`、`working`、`finished` 等语义事件，不直接操作具体帧。
- **生成模块：** 把照片分析、设定图生成、动作生成、清理和打包拆成可替换步骤，避免绑定单一图像模型。
- **隐私策略：** 默认只保留完成桌宠所需的派生资源；原照片是否保留由用户选择，并提供删除入口。

不建议首版直接采用 Live2D：单张照片无法稳定自动生成可用的分层稿和参数绑定，制作成本也明显高于逐帧动画。后续若需要更丝滑的视线追踪和大量动作，再将确认后的角色拆层并升级到骨骼方案。

## 9. 验收标准

### 9.1 视觉验收

- 不看原照片时，四个状态能在 1 秒内被正确辨认。
- 与确认设定稿比较，发型、发色、瞳色、服装主色和关键配件保持一致。
- 正常显示尺寸下，脸部、手部和道具没有明显畸形或闪烁。
- 每个循环连续播放 30 秒无明显跳帧、漂移、白边或背景残留。
- 相邻状态切换不会突然缩放、瞬移或改变光源。

### 9.2 性能验收

- 状态触发到可见响应不超过 150 ms。
- 空闲时不进行不必要的高频重绘。
- 动画播放目标为 12～24 FPS；首版推荐 12 FPS 美术帧配合稳定定时器。
- 常用状态预加载，切换时不访问网络。
- 在目标 Windows 设备上连续运行 2 小时，无持续内存增长和明显 CPU 占用异常。

### 9.3 功能验收

- 四个主状态和五个关键过渡均可通过调试面板手动触发。
- 鼠标快速进出不会导致状态闪烁。
- 任务失败、取消和超时后能正确退出忙碌状态。
- 拖拽位置、多显示器缩放和重启后的配置恢复正常。
- 缺失或损坏资源时回退到默认桌宠，不导致程序崩溃。

## 10. 里程碑

| 里程碑 | 主要工作 | 完成标志 |
| --- | --- | --- |
| M1：规范与原型 | 确定视觉风格、输入规范、状态机和资源协议 | 可用占位图切换四种状态 |
| M2：单角色闭环 | 完成一张照片到设定稿、关键帧和 Idle 动画 | 用户通过审阅关卡 1，Idle 可运行 |
| M3：完整动作集 | 完成 Hover、Loading、Working 和过渡动画 | 四状态在调试面板稳定切换 |
| M4：自动打包与质检 | 实现切帧、清理、manifest 和自动检查 | 新角色资源可一键导入 |
| M5：体验验收 | 性能、鼠标交互、多屏和长时间运行测试 | 达到第 9 节全部验收项 |

## 11. 风险与应对

| 风险 | 影响 | 应对方式 |
| --- | --- | --- |
| 单张照片看不到完整服装或侧面 | 生成内容含推测，可能不符合预期 | 在设定稿阶段显式确认推测部分 |
| 各状态角色长相漂移 | 桌宠缺乏统一身份 | 锁定设定稿、统一姿势表、只重做异常帧 |
| AI 补帧造成手部和饰品闪烁 | 动画观感差 | 减少复杂细节，关键区域人工清理 |
| 状态切换频繁 | 动作被截断、视觉抖动 | 使用优先级、迟滞时间和可中断帧 |
| 透明窗口兼容性问题 | 点击、拖拽或缩放异常 | 先锁定 Windows 目标版本，加入多 DPI 测试 |
| 照片隐私与肖像权 | 合规和信任风险 | 明示用途、最小化保存、支持删除、禁止无授权人物 |

## 12. 建议由你审阅并确认的决策

在进入实现前，建议确认以下默认选择：

1. **形象比例：** 默认 2.5～3 头身 Q 版，是否符合预期。
2. **工作道具：** 默认使用悬浮终端；如有明确的职业主题，再替换为对应的专属道具。
3. **服装来源：** 默认忠于照片；照片信息不足时使用简洁主题服装。
4. **动画路线：** 首版采用透明逐帧动画，后续再评估 Live2D。
5. **目标平台：** 首版优先 Windows；若同时支持 macOS，需要单独安排窗口行为测试。
6. **生成边界：** 是由系统自动生成到可用成品，还是保留美术人员修帧环节。若追求接近商业成品的稳定度，建议保留人工修帧。

确认这些决策后，可将 M1 拆成具体开发任务，并先用占位角色验证状态机与透明窗口，再接入真实照片生成流程。
